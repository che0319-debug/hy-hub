# 規劃書人讀稿｜編寫契約（共用、不去識別專案）

這份契約給「正式文件產出前的語意編輯」。前端 renderer 只忠實呈現人讀稿，不靠固定關鍵字假裝讀懂所有專案，也不為單一專案改程式。

兩件事分開：

1. **語意編輯**（本稿）：把正式規劃整理成真人能看懂的 Markdown。沿既有 Google Doc／Markdown 工作流。不加服務、資料庫、LLM API、審批流程；不每案改前端。
2. **前端呈現**：`planDocumentHtml(..., { layout: 'slate' })` 依標題分類、摘要先行、技術／附錄折疊。不發明專案事實，不改核定狀態。

正式 Google Doc 仍是來源。人讀稿若尚未寫回正式文件，必須標「閱讀整理稿／不變更核定／不是即時進度」。版本與狀態欄位跟原文走。

## 首屏必答（繁中白話）

`## 一頁摘要` 用這四條，標籤用粗體加全形冒號，renderer 會排成卡片：

- **要得到什麼成果**：結案時真人看得到什麼。寫規劃目標，不寫未核實的完成。
- **下一步誰做**：下一件規劃步驟、誰執行。沒有 live 進度就寫規劃值。
- **卡在哪**：現在擋前進的事。分開「規劃已寫的缺口」和「執行現況」（現況未核實就明說）。
- **哪些真要〔負責人〕決定**：只列負責人必須拍板的題。內部實作、工具、測試缺口放「技術待釐清」，不要丟給負責人。

沒有即時執行狀態時，摘要開頭用一句話帶出目標，並寫：

以下為計畫，實際完成狀態未核實。

四條答案保持短句，讓桌面首屏看得到至少兩張卡、手機往下滑一點就看到四張。不要把第一條答案再複製成導言。

不要編造「已開工／已完成／已通過」。日期、狀態、期限是文件記載，不是 Office 即時欄位。

## 正文怎麼寫

- 保留範圍、分工、里程碑、可理解驗收。
- 重複護欄整併一次，不要每個里程碑再貼一次。
- 縮寫第一次出現用白話解釋，或移到附錄。
- 三欄分開，不要混在「待你決定」：
  - **已定案**／已拍板
  - **待決事項**（只放負責人要答的）
  - **技術待釐清**（執行面；可當待決小節，標題寫明不是負責人現在要拍板）
- 白話主文**不冒充新核定規格**。新增推論或整理發現標【整理發現，非正式核定】。
- 不要用漂亮摘要替代證據。

## 附錄必留

`## 附錄`（或標題含「原文留存」）放完整正式原文：表格、程式碼、JSON、HTML 註解、修訂對照。用四個波浪線圍欄包住全文，避免原文裡的三反引號圍欄被拆開：

~~~~
（完整原文）
~~~~

Renderer 會把附錄折疊。展開後可核對。缺來源的句子不要寫進主文。

## 稿頭欄位

人讀稿開頭用列表（renderer 讀成頁首）：

- 稿別：閱讀整理稿（不變更核定、不是即時進度）
- 狀態：（原文狀態，不改）
- 日期：（原文日期）
- Owner／PI：
- 期限：（標規劃值）

合成測試稿必須寫「合成fixture，非真實業務」。

## Renderer 會認的標題（呈現用，不是語意引擎）

| 標題含 | 呈現 |
| :---- | :---- |
| 摘要／總覽／summary | 一頁摘要，放最前 |
| 範圍／交付／目標與終點 | 範圍 |
| 分工／負責／角色 | 分工 |
| 評分／計分 | 評分 |
| 里程碑／時程 | 里程碑 |
| 驗收／交件 | 驗收 |
| 例行／週期 | 例行 |
| 待決／待釐清／待答 | 待決（琥珀框） |
| 已定案／已拍板／決策 | 決策 |
| 護欄／原則 | 護欄 |
| 附錄／原文留存 | 折疊附錄 |
| 資料結構／契約／API／JSON | 折疊技術原文 |

標題含「摘要／總覽／summary」的章節都會被提前當一頁摘要。主文其他節不要用這些詞。主文技術說明若要保持展開，也不要用會折疊的詞當標題（例如用「資料與工具」而不是「資料結構」或「API 契約」）。

## 不做

- 不把人讀稿寫進 GitHub，若內容含真實私人規劃。
- 不改正式 Google Doc、Drive、Office 欄位，除非另有寫入核准。
- 不在 renderer 硬編專案名、PASS、日期、Bot 名單。
- 不新增服務、資料庫、LLM API、每案程式、審批。
- 不把內部實作問題列成負責人待辦。
